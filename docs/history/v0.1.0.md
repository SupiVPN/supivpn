# SupiVPN v0.1.0

First stable SupiVPN release. It promotes the tested `v0.1.0-rc.9` commit without source or database migration changes.

## Implemented features

- **VPN and SSO:** OpenVPN Community 2.7.7 with `tls-crypt-v2`, browser-based SAML 2.0 authentication, and no client certificates.
- **Profile downloads:** SAML-authorized client profiles from the same Okta SAML application tile; no separate Bookmark App required.
- **Group authorization:** explicit group priorities and multiple address pools per group and cluster node.
- **Active-active clusters:** shared PostgreSQL state, heartbeat leases, bounded EC2 fencing/autoheal, maintenance controls, and controlled recovery from blocked states.
- **Session policies:** per-group concurrent connection and duration limits, enforcement of IdP session expiry, and reconnect with fresh SAML authentication after expiry.
- **Component isolation:** separate public, agent, and recovery Lambdas with distinct IAM/database privileges; IAM-authenticated agent API and standalone VM controller support.
- **Database reliability:** PostgreSQL 18 persistence, replay protection, versioned migrations, reconnection, and configurable TLS verification including `verify-full` with a separate server name.
- **Release delivery:** ARM64 as the primary platform, AMD64 support, signed Git commits/tags, and checksum-verified versioned packages.

## Compatibility and limitations

Upgrading from `v0.1.0-rc.9` introduces no new configuration or schema changes. Earlier versions must follow the schema and Lambda isolation requirements below.

Failover reconnects with a new SAML login and IP; existing TCP sessions are not preserved. VPN server DNS SAN verification in OpenVPN Connect remains blocked on client support. Automated wrapping-key rotation, individual profile revocation, and an independent SAML/XMLDSig audit remain future work. See the [security model](../SECURITY_MODEL.md).

## Package compatibility

- Targets: `linux-arm64` (primary), `linux-amd64`
- Bundle format: `3`
- Database schema: `9`; compatible VM schemas: 7, 8, 9
- Public, agent and recovery Lambdas require schema `9`, separate roles and a controlled cutover from the combined Lambda.
