# SupiVPN v0.3.0

## Flow correlation

- A stable JSON `trace_id` follows each VPN connection across the agent, public SAML controller and agent API: authentication, decision delivery/acknowledgement, tunnel establishment, TLS rekey, expiry/operator drop, and disconnect/cancellation.
- Retries and controller replicas retain the ID. New connections receive a new ID even when OpenVPN reuses a CID. Profile downloads have their own correlated flow.
- IDs use the W3C/OpenTelemetry 16-byte representation. They are reconstructed from a domain-separated hash of an existing random login ticket, without logging the ticket or its database lookup hash. Incoming trace headers cannot override a flow ID.
- Additional events cover connection requests, successful TLS rekeys and committed agent API operations. Unbound browser refusals use independent request traces.
- No tracing SDK, spans or exporter are enabled yet. The same ID can be reused when OpenTelemetry instrumentation is added. Native OpenVPN logs remain a separate text stream; node-wide recovery is correlated by node/generation.

## Upgrade from v0.2.0

No database migration, configuration, IAM or API changes are needed. JSON schema 1, database schema 9 and bundle format 3 are unchanged. Keep existing log destinations and retention; preserve the optional `trace_id` field as an exact-match string in collectors. Older components remain compatible during rolling updates but do not emit the new field.

## Validation

Unit/race tests, PostgreSQL 18 integration including two nodes and controller replicas, OpenVPN 2.7.8 tests on ARM64 and AMD64, vet, builds, source/binary vulnerability checks, and source/language audits passed locally. The release uses the same commit and packages verified by the successful main pipeline, with a signed Git tag.

See [the logging and collection contract](../LOGGING.md).

## Package compatibility

- Targets: `linux-arm64` (primary), `linux-amd64`
- Bundle format: `3`
- Database schema: `9`; compatible VM schemas: 7, 8, 9
- Public, agent and recovery Lambdas require schema `9`, separate roles with a controlled cutover only when upgrading from a combined-Lambda deployment.
